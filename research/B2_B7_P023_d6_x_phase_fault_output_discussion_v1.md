# If the matching is already known, can a decoder still be wrong at its final XOR?

It is tempting to stop verification when MWPM returns a plausible set of edges. But a streaming decoder does not expose “a set of edges” to the quantum controller—it exposes detector corrections and logical-observable flips. A stale or phase-misaligned fault map can turn a correct matching into a wrong correction at the last step.

We added a sparse phase-banked output path to the real Micro Blossom `DistributedDual` component. Each edge carries at most two fault IDs. Opening, steady, and closing select 229-, 246-, and 789-bit correction spaces, and every phase transition clears the accumulator before selected subgraph edges are XORed into it.

The result has two deliberately different tests:

1. Exhaustive local map test: all 11,286 phase/edge combinations pass, including 1,682 inactive edges that must map to nothing.
2. Complete-output test: 12 frozen zero/p50/p99/maximum second-pass MWPM subgraphs, containing 104 selected edges, reproduce the public correction vectors bit-for-bit in RTL.

Here is the unresolved question: **where should the trust boundary sit?**

- Is it sufficient to prove the primal subgraph and output-map accumulator independently, then compose their contracts?
- Or must the exact Rust primal + RTL dual execution that chose the subgraph stream those same edge IDs directly into the accumulator in one end-to-end run?
- What minimal trace would reveal a one-phase stale fault map without storing the entire correction vector?

We are taking the stricter position. The current evidence closes the phase-banked map/readout gate, but not end-to-end correction: the compared subgraphs were generated by the already accepted software second pass, not yet by the phase-aware `DistributedDual` plus Rust primal host. That integration is the next falsifier.
