# When an 8-bit input becomes a 24-bit decoder, which width should hardware actually prove?

The last holdout established something useful but narrower than its shorthand suggested: 8-bit detector-error probabilities preserved every software answer. A pinned-source audit then found that PyMatching rescales the merged base graph and internally derived correlation weights into a much wider integer domain.

So the next experiment removes that hidden freedom. Every base edge and every second-pass replacement must live on one explicit even-integer grid. The all-zero preflight says the honest stored range is `142..264` for base edges and `0..164` for implied weights—nine bits, with three graph/rule images per basis.

The source audit also found a sharper hardware blocker: pinned Micro Blossom reserves `LoadWeightsExternal`, but the dynamic edge update remains `TODO`, its external write ports are commented, and the embedded solver rejects nonempty dynamic weights.

Heuristic question: should the next architecture ship every 9-bit replacement over a bus, or broadcast a handful of causal first-pass edges into a resident correlation table beside the edge registers? What is the smallest RTL change that makes the reserved load path real without extending the exact-matching critical path?

After this public freeze binds new X/Z seeds, 1,024 fresh shots per basis must reproduce the high-precision online and full-block frames exactly, with zero commit/final residuals. Even a pass is only a software semantic bridge: no Micro Blossom RTL, cycles, FPGA timing, full B2, scalable #023, or B7 resource credit is claimed.
